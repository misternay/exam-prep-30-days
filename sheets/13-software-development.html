1. ต้องเข้าใจ

SDLC (Software Development Life Cycle)

  • เฟสหลัก: Requirements → Design → Implementation → Testing → Deployment → Maintenance (วนซ้ำได้ ไม่ใช่เส้นตรงตายตัว)
  • Waterfall: ทำเฟสต่อกันจบทีละเฟส เอกสารครบ — เหมาะงานที่ข้อกำหนดนิ่ง/สัญญาชัด (เช่นงานภาครัฐบางประเภท); ข้อเสีย: เปลี่ยนยาก, เห็นผลช้า
  • Agile: ทำเป็นรอบสั้น ได้ผลลัพธ์ใช้งานได้บ่อย, ตอบการเปลี่ยนแปลง — ไม่ได้แปลว่าไม่วางแผน (แค่แผนปรับได้)

Agile Manifesto 4 ค่า (ท่อง)

  • Individuals & interactions over processes & tools
  • Working software over comprehensive documentation
  • Customer collaboration over contract negotiation
  • Responding to change over following a plan
  • โน้ต: ของซ้ายมีค่ามากกว่า แต่ไม่ได้แปลว่าของขวาไร้ค่า — คำถามหลอกชอบใช้

Scrum (รู้ให้ครบ 3 หมวด)

  • Roles: Product Owner (จัดลำดับคุณค่า/backlog), Scrum Master (โค้ช/ขจัดอุปสรรค — ไม่ใช่เจ้านายทีม), Developers (ทำ increment)
  • Artifacts: Product Backlog (รายการทั้งหมด), Sprint Backlog (ที่เลือกทำใน sprint), Increment (ของที่เสร็จตาม Definition of Done)
  • Events: Sprint (timebox ไม่เกิน 1 เดือน — Scrum Guide 2020) → Sprint Planning (เลือกงาน+เป้า) → Daily Scrum (15 นาที sync) → Sprint Review (โชว์ของให้ stakeholder) → Retrospective (ปรับกระบวนการ)
  • เน้น empiricism: transparency, inspection, adaptation

แนวทางอื่นที่ควรรู้จัก

  • Kanban: ไม่มี sprint ตายตัว — ไหลงานต่อเนื่อง, จำกัด WIP, วัด lead time/cycle time, บอร์ดคอลัมน์ (To Do/Doing/Done) — เหมาะงาน ops/support/งานไหลเข้าไม่คงที่
  • XP (Extreme Programming): pair programming, TDD, CI, small releases, refactoring — เน้นเทคนิคระดับโค้ด
  • ผสมได้: Scrum ครอบ Kanban ภายใน หรือ Scrumban

Requirements

  • Functional — ระบบต้องทำอะไร (“ผู้ใช้รีเซ็ตรหัสผ่านได้”)
  • Non-functional — คุณสมบัติคุณภาพ (“ตอบใน 200ms ที่ p95”, “รองรับ 1000 concurrent”, security, usability) — ข้อสอบชอบโจทย์สลับหมวด
  • User story: “ในฐานะ <บทบาท> ฉันต้องการ <ความสามารถ> เพื่อ <คุณค่า>” + acceptance criteria (เงื่อนไขผ่าน — มักเขียน Given/When/Then)
  • INVEST (invest คุณภาพ story): Independent, Negotiable, Valuable, Estimable, Small, Testable
  • งานต้องชัดก่อนเริ่ม (Definition of Ready) และชัดว่าเสร็จ (Definition of Done: code review, test ผ่าน, deploy ได้, เอกสารอัปเดต)

Estimation & Planning

  • Story points — วัด “ขนาด/ความซับซ้อน” แบบสัมพัทธ์ (fibonacci 1,2,3,5,8…) ไม่ใช่ชั่วโมง; Planning poker — เปิดพร้อมกันแล้วคุยจุดที่ต่างกัน
  • Velocity — points ที่ทีมทำได้ต่อ sprint (ใช้วางแผนคร่าวๆ ห้ามใช้กดดัน/เทียบข้ามทีม)
  • Burndown chart — งานเหลือลงตามเวลาใน sprint; Burnup — งานเสร็จสะสมแบบขึ้น

Tech debt & กระบวนการคุณภาพในทีม

  • Tech debt — หนี้เทคนิคจากทางลัด (โค้ดไม่ทดสอบ, เลี่ยง design) ดอกเบี้ย = แก้ช้าลงทุกวัน; บริหารโดย log เป็น backlog item + จ่ายคืนเป็นระยะ; ไม่ใช่ทุกหนี้ต้องจ่าย
  • Code review — purpose: จับ bug, แชร์ความรู้, รักษามาตรฐาน; PR เล็ก (~400 บรรทัด) review ได้จริง
  • ADR (Architecture Decision Record) — จดการตัดสินใจสำคัญ: บริบท/ทางเลือก/ตัดสินใจ/ผลที่ตามมา — กันทีมใหม่ถามซ้ำ
  • Boy scout rule — เห็นของสกปรกเล็กๆ ในโค้ดที่แตะ เก็บกวาดไปด้วย

Architecture scale & API (ทวนเชื่อม 02)

  • วิวัฒนาการ: monolith → modular monolith → microservices; เลือกตามขนาดทีม/ความต้องการ scale แยกส่วน; microservices แลกมาด้วย network, distributed transaction, ops หนักขึ้น
  • Semantic Versioning: MAJOR(breaking).MINOR(feature เพิ่มแบบ compatible).PATCH(bugfix) — 0.x = ยังไม่ stable
  • REST sanuk: ดูหัวข้อ 02; idempotency ของ GET/PUT/DELETE สำคัญต่อ retry ที่ปลอดภัย

2. ต้องจำ

  • SDLC 6 เฟส; waterfall vs agile ข้อดี/ข้อเสียสั้นๆ
  • Agile Manifesto 4 คู่ค่า
  • Scrum: roles 3, artifacts 3, events 5 (Planning, Daily, Review, Retro + Sprint ตัวกรอบ)
  • Sprint = timebox ไม่เกิน 1 เดือน (Guide 2020 เลิกใช้กรอบ 2–4 สัปดาห์แบบตำราเก่า; ของจริงนิยม 1–2 สัปดาห์)
  • Kanban = WIP limit + flow; XP = TDD/pair/CI
  • Functional vs non-functional (ตัวอย่างทั้งคู่); story format + Given/When/Then
  • Story points = relative; velocity ไม่ใช้เทียบทีม
  • Semver MAJOR.MINOR.PATCH ความหมาย

3. กับดักข้อสอบ

  • “Agile = ไม่มีเอกสาร/ไม่วางแผน” — ผิด; Agile ให้คุณค่ากับ working software มากกว่าเอกสาร แต่ยังต้องมีเท่าที่จำเป็น
  • Scrum Master ไม่ใช่ project manager/เจ้านาย — เป็น facilitator/coach
  • Daily ไม่ใช่รายงานความคืบหน้าถึงหัวหน้า — คือการ sync ทีม + วางแผนวัน
  • Sprint Review (ดูของ/demo กับ stakeholder) vs Retrospective (ดูกระบวนการภายในทีม) — อย่าสลับ
  • “Non-functional ทีหลังได้” — ผิด; ราคา/สถาปัตย์ตัดสินแต่ต้น (performance/security เป็นต้นทุนที่ฝัง)
  • Story points ไม่เทียบข้ามทีม (คนละ yardstick)

4. Self-check (ปิดหน้า ตอบก่อน)

Q1: SDLC มีเฟสอะไรบ้างA: Requirements → Design → Implementation → Testing → Deployment → Maintenance (ทำซ้ำได้ใน agile)
Q2: Agile Manifesto 4 คุณค่าA: คน&ปฏิสัมพันธ์ > กระบวนการ&เครื่องมือ; ซอฟต์แวร์ทำงานได้ > เอกสารครบ; ร่วมมือลูกค้า > เจรจาสัญญา; ตอบการเปลี่ยนแปลง > ทำตามแผน
Q3: Scrum มี roles/artifacts/events อะไรบ้างA: Roles: PO, SM, Developers · Artifacts: Product Backlog, Sprint Backlog, Increment · Events: Sprint, Planning, Daily, Review, Retrospective
Q4: Kanban ใช้เมื่อไร ต่างจาก Scrum ยังไงA: งานไหลต่อเนื่อง/หลากหลาย (support, ops) — ไม่มี sprint/timebox, เด่นที่ WIP limit และ lead time; Scrum มี timebox + roles/events ชัด
Q5: “ระบบรองรับผู้ใช้พร้อมกัน 500 คน” เป็น requirement ชนิดไหนA: Non-functional (performance/scale) — ระบุคุณภาพ ไม่ใช่ฟังก์ชัน; ฟังก์ชันจะแนว “ทำอะไรได้”
Q6: Story points ต่างจากชั่วโมงยังไง และทำไมไม่เทียบข้ามทีมA: Points วัดขนาดแบบสัมพัทธ์ของทีมนั้น (relative sizing) ไม่ผูกเวลา — สเกลของแต่ละทีมไม่เหมือนกัน เทียบข้ามทีมจึงไร้ความหมาย
Q7: Semver บอกอะไร: 2.4.1 → 3.0.0A: MAJOR ขยับ = มี breaking change; MINOR = ฟีเจอร์ใหม่ compatible; PATCH = แก้บั๊ก — ผู้ใช้ต้องอ่าน/ทดสอบก่อนอัป major
