อ่าน ~35 นาที · อ้างอิงหลัก: refactoring.guru (patterns), Clean Architecture (Martin), DDD (Evans)

1. ต้องเข้าใจ

เป้าหมายของการออกแบบ

  • ลด coupling (การพึ่งพากันระหว่างโมดูล) + เพิ่ม cohesion (แต่ละโมดูลทำเรื่องเดียวที่เกี่ยวกัน) — นี่คือคำตอบของโจทย์ design เกือบทุกข้อ
  • ออกแบบเพื่อ “แก้ไขได้” ไม่ใช่เพื่อ “สวย” — โค้ดจะถูกอ่านและแก้มากกว่าถูกเขียน
  • Composition over inheritance — ประกอบพฤติกรรมด้วย object composition ยืดหยุ่นกว่า inherit ลึกๆ

SOLID (ท่องให้ได้ทุกตัว)

ตัวชื่อใจความอาการที่ละเมิด
SSingle Responsibilityคลาสมีเหตุผลเดียวที่จะต้องถูกแก้ (one reason to change)คลาสเดียวทำทั้ง DB + คำนวณ + ส่งอีเมล
OOpen/Closedเปิดให้ขยาย ปิดไม่ให้แก้ (เพิ่มความสามารถด้วยโค้ดใหม่)ทุกครั้งที่เพิ่ม type ต้องแก้ if/else chain เดิม
LLiskov Substitutionคลาสลูกต้องแทนที่คลาสแม่ได้โดยไม่พังความถูกต้องSquare extends Rectangle แล้วเปลี่ยน behavior (getArea ผิด)
IInterface Segregationหลาย interface เล็ก ดีกว่า interface ใหญ่ที่บังคับให้ implement ของที่ไม่ใช้interface 20 เมธอด แต่คลาสใช้จริง 2
DDependency Inversionพึ่ง abstraction ไม่พึ่ง implementation (high-level ไม่รู้จัก low-level)Service new MySQLRepo() ตรงๆ แทน inject interface

หลักการเพื่อนบ้าน

  • DRY — อย่าเขียนความรู้เดิมซ้ำ (แต่ระวัง over-DRY: โค้ดเหมือนกันเพราะบังเอิญ ≠ duplication ที่ต้องรวม)
  • KISS / YAGNI — ทำให้ง่าย / อย่าสร้างสิ่งที่ “อาจจะได้ใช้” (ข้อสอบชอบให้ pattern ที่ไม่จำเป็น เป็นกับดัก)
  • SoC (Separation of Concerns) — แยก concern เช่น UI / business logic / data

Design patterns ที่ต้องรู้ชื่อ + แก้ปัญหาอะไร

  • Creational: Factory Method (สร้างโดยไม่ผูกคลาสจริง), Abstract Factory (family ของ object), Builder (ประกอบทีละขั้น), Singleton (instance เดียว — ระวัง test ยาก/global state), Prototype (โคลน)
  • Structural: Adapter (แปลง interface ให้เข้ากัน), Decorator (ห่อเพิ่มพฤติกรรมโดยไม่แก้เดิม), Facade (หน้าเรียบง่ายปิด subsystem), Proxy (แทนตัวจริง คุมการเข้าถึง), Composite (ต้นไม้ของส่วน/ทั้งหมด), Bridge (แยก abstraction จาก implementation)
  • Behavioral: Strategy (สลับ algorithm), Observer (pub/sub แจ้งผู้ฟัง), Command (ห่อคำขอเป็น object — undo ได้), State (เปลี่ยนพฤติกรรมตาม state เครื่องจักร), Template Method (โครงในคลาสแม่ ช่องให้ลูกเติม), Iterator, Chain of Responsibility
  • ข้อสอบที่ออกบ่อย: ให้สถานการณ์มา ถามว่าใช้ pattern ไหน — จำคีย์เวิร์ด: “สลับได้ runtime” = Strategy; “แจ้งหลายฝ่ายอัตโนมัติ” = Observer; “สร้างโดยไม่รู้ concrete class” = Factory; “เพิ่มความสามารถซ้อนได้” = Decorator; “interface ไม่เข้ากัน” = Adapter

Architecture

  • Layered — presentation / application / domain / infrastructure; ข้อเสียถ้าไล่พึ่งกันลงล่างตรงๆ = domain ผูกกับ DB
  • Hexagonal (Ports & Adapters) — แกนกลาง business logic ไม่รู้จักโลกภายนอก; ติดต่อผ่าน port (interface) และ adapter (implementation)
  • Clean Architecture — ชั้นซ้อนกัน, dependency rule: พุ่งเข้าหาแกนกลางเสมอ; ข้างในไม่รู้จัก framework/DB/UI
  • ข้อโต้แย้ง: microservices ให้ independent deploy/scale แต่เพิ่ม network/ops/consistency complexity — เริ่ม monolith แบบ modular ก่อนได้

DDD พื้นฐาน

  • Entity — มี identity ตามเวลา; Value Object — ไม่มี identity เปรียบเทียบกันที่ค่า (Money, Email)
  • Aggregate — กลุ่ม entity ที่ต้องสอดคล้องกันใน transaction เดียว, แก้ผ่าน root เดียว (Aggregate Root)
  • Bounded Context — ขอบเขตที่คำๆ หนึ่งมีความหมายเฉพาะ (คำว่า “ลูกค้า” คนละโมเดลใน Sales vs Support)
  • Ubiquitous Language — คุยกับ domain expert ด้วยภาษาเดียวที่ใช้ในโค้ด
  • CQRS — แยกโมเดลอ่าน/เขียน; Event Sourcing — เก็บลำดับ event เป็น source of truth แล้วสร้าง state จาก replay

API design (REST)

  • Resource + HTTP verb: GET อ่าน, POST สร้าง (ไม่ idempotent), PUT แทนที่ทั้งก้อน (idempotent), PATCH แก้บางส่วน, DELETE ลบ (idempotent)
  • Status: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthenticated, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Validation, 429 Too Many Requests, 500 Internal, 503 Unavailable
  • Versioning (/v1), pagination, error body มี structure เดียวกัน, list filter เป็น query param

2. ต้องจำ

  • SOLID ตามตารางด้านบน + หนึ่งบรรทัดต่อตัว (เขียนอธิบายจากความจำได้)
  • Coupling ↓ Cohesion ↑
  • Clean Architecture dependency rule — พุ่งเข้าในเสมอ
  • Pattern keyword map: Strategy=สลับ algorithm · Observer=แจ้งหลายฝ่าย · Factory=สร้างโดยซ่อน concrete · Decorator=ห่อเพิ่มพฤติกรรม · Adapter=แปลง interface · Facade=หน้าเดียวปิดระบบ · Singleton=เดียวทั้งระบบ · Command=คำขอเป็น object
  • Entity vs Value Object — identity vs value
  • Semver: MAJOR = breaking, MINOR = เพิ่มแบบ compatible, PATCH = fix

3. กับดักข้อสอบ

  • “Open/Closed” ไม่ได้แปลว่า “ห้ามแก้โค้ดเลย” — แปลว่าเพิ่มฟีเจอร์ใหม่ด้วยการ “เพิ่มโค้ด” มากกว่าไปแก้ logic เดิม
  • Square/Rectangle เป็นตัวอย่างข้อสอบ LSP ยอดนิยม — ต้องอธิบายว่าทำไมแทนที่แล้วพัง
  • Factory Method กับ Abstract Factory ต่างกัน: อันแรกสร้าง “หนึ่งผลิตภัณฑ์” อันหลังสร้าง “ตระกูลผลิตภัณฑ์”
  • Singleton ไม่ใช่ pattern ที่ควรชู — ในข้อสอบเชิงวิพากษ์ให้บอกข้อเสีย (global state, ซ่อน dependency, test ยาก)
  • “inherit เพื่อ reuse” ผิดหลัก — reuse ด้วย composition; inherit เมื่อความสัมพันธ์เป็น “is-a” จริงเท่านั้น

4. Self-check (ปิดหน้า ตอบก่อน)

Q1: อธิบาย SOLID ครบ 5 ตัวในหนึ่งประโยคต่อตัวA: S=เหตุผลเดียวในการแก้; O=ขยายได้โดยไม่แก้เดิม; L=คลาสลูกแทนที่แม่ได้; I=interface เล็กตามผู้ใช้; D=พึ่ง abstraction ไม่พึ่ง concrete
Q2: Coupling กับ cohesion คืออะไร ทิศทางที่ดีA: Coupling=การพึ่งพาระหว่างโมดูล (อยากได้น้อย); cohesion=ความเกี่ยวเนื่องภายในโมดูล (อยากได้มาก)
Q3: Dependency Rule ของ Clean Architecture คืออะไรA: dependency ต้องพุ่งเข้าหาชั้นใน (business core) เสมอ — ชั้นในไม่รู้จัก framework/DB/UI
Q4: Strategy ต่างจาก State ยังไงA: Strategy เปลี่ยน algorithm ที่ใช้ (มักเลือกจากนอก), State เปลี่ยนพฤติกรรมตาม internal state และ state เปลี่ยนตัวเองได้ตาม transition
Q5: Square extends Rectangle ละเมิดหลักอะไร ทำไมA: LSP — โค้ดที่ใช้ Rectangle ส่ง setWidth/setHeight อิสระจะพังเมื่อเป็น Square (พฤติกรรมเปลี่ยนไป)
Q6: Entity กับ Value Object ต่างกันที่อะไรA: Entity มี identity (id เดิม = ตัวเดิม แม้ attribute เปลี่ยน), Value Object เท่ากันที่ค่า — เปลี่ยนค่า = คนละค่า ใช้แทนกันได้เลย
Q7: เมื่อไรเลือก monolith แทน microservicesA: ทีมเล็ก/ยังไม่ชัดขอบเขต domain/ไม่ต้องการ scale แยกส่วน — เพราะ microservices เพิ่ม network latency, distributed transaction, ops burden
