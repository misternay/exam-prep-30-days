03 · Security & Secured Dev

อ่าน ~45 นาที · อ้างอิงหลัก: OWASP Top 10:2025 (top10.owasp.org), OWASP Cheat Sheets, OAuth 2.0 (RFC 6749) / OIDC

1. ต้องเข้าใจ

เป้าหมายความปลอดภัย

  • CIA triad: Confidentiality ( secrecy — เข้ารหัส/คุมสิทธิ์), Integrity (ข้อมูลไม่ถูกแก้โดยไม่ได้รับอนุญาต), Availability (ระบบใช้ได้ — กัน DoS)
  • เสริม: Authentication, Authorization, Non-repudiation (ปฏิเสธไม่ได้ว่าทำ — ลายเซ็น/log)
  • Defense in depth — หลายชั้นป้องกัน อย่าพึ่งชั้นเดียว; Least privilege — ให้สิทธิ์เท่าที่จำเป็น; Fail-safe defaults — พังแล้วต้องปิด (deny) ไม่ใช่เปิด

OWASP Top 10:2025 — ท่อง (ฉบับปัจจุบัน)

  1. A01 Broken Access Control — ผู้ใช้ทำเกินสิทธิ์ (IDOR, path traversal); SSRF ถูกยุบเข้ามารวมหมวดนี้ — ยังครองอันดับ 1
  2. A02 Security Misconfiguration — default ไม่ปลอดภัย, debug เปิด, S3 public, verbose error (ขยับจาก #5 ขึ้นมา #2)
  3. A03 Software Supply Chain Failures — dependency / build system / ช่องทางแจกจ่าย ถูกโจมตี (ต่อยอดจาก Vulnerable & Outdated Components เดิม)
  4. A04 Cryptographic Failures — เข้ารหัสอ่อน/ไม่เข้ารหัสข้อมูลสำคัญ, MD5/SHA1, hardcode key → TLS, at-rest encryption, algorithm ทันสมัย
  5. A05 Injection — SQL/Command/NoSQL + XSS (XSS=ถี่สูง/ผลต่ำ, SQLi=ถี่ต่ำ/ผลสูง) → parameterized queries, แยกคำสั่งจากข้อมูล
  6. A06 Insecure Design — ออกแบบขาด threat model เช่น ไม่มี rate limit, ไม่มี recovery flow
  7. A07 Authentication Failures — ไม่มี MFA, password อ่อน, session ไม่หมดอายุ (ชื่อย่อลงจาก Identification & Authentication เดิม)
  8. A08 Software or Data Integrity Failures — deserialize ของไม่น่าเชื่อถือ, artifact/อัปเดตไม่ตรวจ signature
  9. A09 Security Logging & Alerting Failures — log/แจ้งเตือนไม่พอ ตรวจจับ breach ไม่ได้ (เดิม Monitoring)
  10. A10 Mishandling of Exceptional Conditions — จัดการ error/edge case แย่: fail-open, error เผยข้อมูล, ไม่ validate กรณีพิเศษ (หมวดใหม่)

AuthN vs AuthZ

  • Authentication = “คุณคือใคร” (login, MFA, session) · Authorization = “คุณทำอะไรได้” (role/permission)
  • Session-based: server เก็บ state + cookie กับ session id (revoke ได้ทันที) · Token-based (JWT): stateless ตรวจที่ลายเซ็น — ข้อเสียคือ revoke ยาก → อายุสั้น + refresh token
  • JWT = header.payload.signature — payload เป็นแค่ Base64 (อ่านได้ ไม่ใช่การเข้ารหัส) ห้ามใส่ข้อมูลลับ; กับดักคลาสสิก: เซิร์ฟเวอร์เช็ค alg จาก token เอง (alg=none attack) → fix: กำหนด algorithm ที่ฝั่ง verify
  • OAuth2 = authorization framework (ให้สิทธิ์แอปเข้าถึงข้อมูล) ไม่ใช่ authentication ตัวมันเอง; roles: Resource Owner, Client, Authorization Server, Resource Server; flow ที่ควรใช้: Authorization Code + PKCE (web/mobile); Client Credentials = server-to-server; Implicit ถูกยกเลิกแล้ว
  • OIDC = ชั้น authentication บน OAuth2 — ได้ ID token (JWT) บอกตัวตนผู้ใช้
  • Password storage: ห้าม plaintext / ห้าม MD5-SHA เดี่ยว; ใช้ bcrypt / scrypt / Argon2 + per-user salt; เพิ่ม rate limit, lockout, ไม่บอกว่า “user ไม่มี” vs “รหัสผิด” (user enumeration)

Secure SDLC — “Secured Dev”

  • Shift left — ตรวจความปลอดภัยตั้งแต่ design/code ไม่ใช่ก่อน release; ถูกกว่าแก้ทีหลังมาก
  • Threat modeling (STRIDE): Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege — ใช้ตั้งคำถาม “อะไรเสียหายได้บ้าง” ตอนออกแบบ
  • เครื่องมือใน pipeline: SAST (อ่าน source หา pattern อันตราย), DAST (ยิงทดสอบระบบที่รันอยู่), SCA (dependency/CVE), secret scanning (กันคีย์หลุด commit), container scanning (image CVE)
  • Secrets management: ห้าม commit secret ลง git (แม้ประวัติ), ใช้ vault/secret manager/env, rotate ได้, สิทธิ์อ่านแบบ least privilege
  • Zero trust — ไม่เชื่ออะไรในเน็ตเวิร์กโดยปริยาย ตรวจทุก request (verify explicitly, least privilege, assume breach)

2. ต้องจำ

  • OWASP Top 10:2025 เรียง A01→A10 (ฉบับปัจจุบัน) — จำเพิ่ม 3 จุดเปลี่ยน: SSRF→A01 · A03=Supply Chain · A10=Exceptional Conditions (ใหม่); ยังต้องรู้ฉบับ 2021 เพราะตำราเก่าอ้างถึง
  • CIA = Confidentiality, Integrity, Availability
  • STRIDE 6 ตัว
  • password hashing: bcrypt/Argon2 + salt (ไม่ใช่ AES/MD5/SHA — พวกนั้นไม่ใช่การ hash สำหรับรหัสผ่าน)
  • flow ที่ควรใช้ใน OAuth2 = Authorization Code + PKCE; OIDC = identity layer
  • Defense in depth / Least privilege / Fail-safe defaults — นิยามสั้น

3. กับดักข้อสอบ

  • “เข้ารหัสด้วย MD5” ผิดทุกกรณี (MD5/SHA ไม่ใช่สำหรับ password); “hash อย่างเดียวไม่ salt” ก็ผิด
  • XSS = ปัญหา “output encoding” ตอน render; SQLi = ปัญหา “แยกคำสั่งจากข้อมูล” — อย่าสลับกัน
  • 401 vs 403: 401 = ยังไม่ได้ยืนยันตัวตน/ไม่ผ่าน; 403 = ยืนยันแล้วแต่ไม่มีสิทธิ์
  • OAuth2 ไม่ใช่ authentication — ถ้าข้อสอบถาม authentication ต้องพูด OIDC
  • HTTPS/TLS ป้องกันการดักฟังระหว่างทาง (in transit) ไม่ได้ป้องกัน SQLi/XSS — คนละชั้น
  • “Escaping” เฉยๆ ไม่ใช่คำตอบของ SQLi ที่ดี — คำตอบหลักคือ parameterized query
  • โจทย์อ้าง “A10 = SSRF” (ฉบับ 2021) ได้ — แต่ฉบับ 2025 SSRF อยู่ A01 และ A10 = Mishandling of Exceptional Conditions: ตอบตามปีที่โจทย์อ้าง

4. Self-check (ปิดหน้า ตอบก่อน)

Q1: อธิบาย CIA triadA: Confidentiality — ข้อมูลเห็นได้เฉพาะผู้มีสิทธิ์; Integrity — ข้อมูลไม่ถูกแก้/ปลอมโดยไม่ได้รับอนุญาต; Availability — ระบบพร้อมใช้งาน
Q2: OWASP A01 (2025) คืออะไร ยกตัวอย่างA: Broken Access Control — เช็คสิทธิ์ไม่ครบ/ทำเกินสิทธิ์ เช่น IDOR; ฉบับ 2025 SSRF ถูกยุบเข้ามารวมในหมวดนี้ด้วย
Q3: เก็บรหัสผ่านยังไงให้ถูกA: Hash ด้วย bcrypt/scrypt/Argon2 พร้อม per-user salt (ปรับ cost ได้), ห้าม plaintext/MD5/SHA เดี่ยว, เพิ่ม rate limiting
Q4: SQLi กับ XSS ต่างกันที่จุดไหน และแก้ต่างกันยังไงA: SQLi = input ปนเข้าไปเป็นคำสั่ง query (แก้: parameterized query); XSS = input ปนเข้าไปเป็น HTML/JS (แก้: output encoding + CSP)
Q5: Authorization Code + PKCE ใช้ทำอะไร ต่างจาก Implicit ยังไงA: flow ที่ปลอดภัยของ OAuth2 สำหรับ public client — แลก authorization code เป็น token; Implicit คืน token ตรงใน redirect (ถูกยกเลิกเพราะ token หลุดได้)
Q6: STRIDE ใช้ทำอะไรA: Threat modeling — ไล่หาภัย 6 แบบ: Spoofing, Tampering, Repudiation, Information disclosure, DoS, Elevation of privilege
Q7: Shift-left หมายถึงอะไร ทำไมA: ย้ายงานตรวจความปลอดภัยไปทางซ้ายของ timeline (design/code แรกสุด) — ต้นทุนแก้ bug ถูกกว่ามากและไม่ติดไป prod
