เข้าใจต้องจำกับดักSelf-check

09 · Quality Engineering

อ่าน ~35 นาที · อ้างอิงหลัก: ISTQB glossary, Google Testing Blog (test pyramid/sizes), xUnit Test Patterns (Meszaros)

1. ต้องเข้าใจ

QA vs QC vs Testing (ศัพท์ที่ข้อสอบชอบแยก)

  • Quality Assurance (QA) — กระบวนการ/ระบบที่ทำให้ “สร้างของดีตั้งแต่แรก” (process-oriented, prevention)
  • Quality Control (QC) — การตรวจผลิตภัณฑ์/ผลลัพธ์ว่าถูกต้องไหม (product-oriented, detection)
  • Testing — กิจกรรมหนึ่งของ QC; quality engineering = รวมทุกอย่าง (process + เทคนิค + เครื่องมือ + วัฒนธรรม)
  • Shift-left — ย้ายกิจกรรมคุณภาพไปทางซ้ายของ timeline (review, static analysis, TDD ตั้งแต่โค้ดแรก) — แก้ก่อนถูกกว่าเสมอ
  • Quality built-in ไม่ใช่ inspected-in — คุณภาพมาจากวิธีทำงาน ไม่ใช่การตรวจท้ายน้ำ

Test pyramid (ท่องรูปและเหตุผล)

  • Unit (ชั้นล่าง — เยอะสุด): ทดสอบฟังก์ชัน/คลาสเดียวแบบ isolate, เร็วมาก (ms), รันใน CI ทุกครั้ง, feedback เร็ว
  • Integration (ชั้นกลาง): ทดสอบการเชื่อมกันของหลาย part (DB, HTTP, message) — ช้ากว่า แต่จับ bug ที่ unit ไม่เจอ (wiring, config, contract)
  • E2E/UI (ชั้นยอด — น้อยสุด): ทดสอบระบบรวมเหมือนผู้ใช้จริง — ช้า, flaky ง่าย, แพง; ใช้เฉพาะ critical path (login, checkout)
  • Anti-pattern: inverted pyramid (E2E เยอะ, unit น้อย) = “ice cream cone” — suite ช้า, พังมั่ว, debug ยาก
  • Test size ของ Google: small/medium/large อิง resource ที่ใช้ (อธิบายเพิ่มได้)

Test doubles (ของปลอมในเทสต์)

ตัวคืออะไรใช้เมื่อ
Dummyค่าอะไรก็ได้ เพื่อเติม argument ให้ครบไม่ถูกเรียกจริง
Stubตอบค่าตายตัวที่เตรียมไว้ควบคุม input ทางอ้อม
Spyห่อของจริง/ของปลอม แล้วบันทึกว่าเรียกอะไรตรวจว่าถูกเรียกไหม
Mockตั้ง expectation: ต้องถูกเรียกแบบนี้ → verifyยืนยัน interaction
Fakeimplementation จริงแบบเบา (in-memory DB, fake SMTP)แทนของหนัก โดยรักษาพฤติกรรมหลัก

TDD & BDD

  • TDD cycle: RED → GREEN → REFACTOR — เขียนเทสต์ที่พังก่อน (RED) → เขียนโค้ดน้อยสุดให้ผ่าน (GREEN) → ปรับโครงโดยเทสต์ยังเขียว (REFACTOR)
  • ประโยชน์: design ดีขึ้น (testable = loosely coupled), เอกสาร behavior, regression safety net
  • BDD: เขียนจากมุมธุรกิจ — Given (สถานะตั้งต้น) When (การกระทำ) Then (ผลที่คาดหวัง) — ผูกกับ acceptance criteria
  • Acceptance criteria — เงื่อนไขที่ต้องจริงเพื่อถือว่า user story เสร็จ; Definition of Done — checklist กว้างระดับทีม (รวม test/review/docs ผ่าน)

มิติคุณภาพอื่น

  • Static analysis: lint, formatter, type check, SAST — จับได้โดยไม่รันโค้ด; เร็ว ถูก รันใน CI ทุก PR
  • Coverage: line vs branch coverage — บอกว่าโค้ด “ถูกแตะ” ไม่ได้บอกว่า “ถูกต้อง”; ใช้หา blind spot ไม่ใช่ตั้งเป็น KPI (coverage สูง + assertion อ่อน = เสแสร้ง)
  • Contract testing — สัญญาระหว่างผู้ให้/ผู้ใช้ API (Pact) จับ breaking change ก่อน deploy
  • Non-functional: performance/load (baseline + p95/p99), stress, security testing, accessibility, reliability — มีเกณฑ์วัดชัด ไม่ใช่ “รู้สึกว่าเร็ว”
  • Smoke test — ชุดสั้นๆ ยืนยันระบบ “มีชีวิต” หลัง deploy; regression test — ชุดที่กันของเก่าพังเมื่อแก้ใหม่

Flaky tests (ศัตรูของทีม) — สาเหตุและทางแก้

  • สาเหตุ: รอเวลาแบบ sleep ตายตัว, พึ่งลำดับการรัน/state ร่วมกัน, ข้อมูลทดสอบไม่ reset, เรียก network จริง, timezone/วันที่, concurrency
  • แก้: ทำให้ deterministic (fake time, seed, isolate data ต่อ test), ไม่พึ่ง shared state, quaranทีนแล้ว fix ทันที — ห้าม rerun จนผ่านแล้วเดินต่อ

2. ต้องจำ

  • Pyramid: Unit เยอะ → Integration กลาง → E2E น้อย + เหตุผล (speed/cost/fragility)
  • TDD cycle RED-GREEN-REFACTOR; BDD = Given-When-Then
  • Test doubles 5: dummy, stub, spy, mock, fake (แยก mock=verify interaction vs stub=ให้ค่า)
  • QA=process, QC=product, Testing=กิจกรรม; shift-left = ย้ายคุณภาพซ้าย
  • Coverage ≠ quality; p95/p99 สำคัญกว่า average เรื่อง performance
  • Flaky test = ต้อง fix ไม่ใช่ทน rerun

3. กับดักข้อสอบ

  • “Mock” กับ “Stub” สลับกันบ่อย: stub = ป้อนค่า, mock = ตรวจว่าถูกเรียกตามคาด — ตอบให้ตรงคำถามว่าให้ค่าหรือ verify
  • “Coverage 100% แล้ว bug ไม่มี” — ผิดชัดเจน; ต้องพูดถึง assertion คุณภาพ + มิติอื่น
  • “E2E เยอะสุดเพื่อความมั่นใจ” — ผิด; กลับ pyramid (ช้า flaky แพง)
  • Integration test ไม่ใช่ “รันเทสต์ทั้งระบบช้าๆ” — คือทดสอบ “การต่อกัน” ของ component; E2E = ทดสอบเส้นทางงานครบผ่านระบบที่ประกอบจริง (จะผ่าน UI หรือ API ก็ได้)
  • TDD ไม่ได้ห้ามออกแบบก่อน — แต่ห้ามเขียน production code ก่อนมีเทสต์ที่พัง (ในลูปสั้นๆ)

4. Self-check (ปิดหน้า ตอบก่อน)

Q1: อธิบาย test pyramid พร้อมเหตุผลแต่ละชั้นA: unit เยอะสุด — เร็ว/ถูก/isolate; integration กลาง — จับปัญหา wiring/contract; e2e น้อย — ใกล้ผู้ใช้จริงแต่ช้า flaky แพง จึงเก็บ critical path
Q2: TDD มี 3 ขั้นอะไรบ้างA: RED — เขียนเทสต์พังก่อน; GREEN — โค้ดน้อยสุดให้ผ่าน; REFACTOR — ปรับโครงโดยเทสต์ยังผ่าน
Q3: Stub ต่างจาก mockA: stub ให้ค่าที่เตรียมไว้เพื่อให้โค้ดเดินต่อ; mock ตั้ง expectation ว่าต้องถูกเรียกแบบไหน แล้ว verify ว่าเกิดจริง (ตรวจ interaction)
Q4: Coverage วัดอะไร และทำไมไม่ควรใช้เป็นเป้าเดียวA: วัดว่าโค้ดส่วนไหนถูกแตะในเทสต์ — ไม่ได้บอกความถูกต้อง (assertion อาจอ่อน/กรณีไม่ครบ) จึงใช้เป็นเครื่องมือหา blind spot
Q5: QA ต่างจาก QCA: QA = กระบวนการป้องกันคุณภาพตั้งแต่ต้น (process); QC = ตรวจผลิตภัณฑ์/ผลลัพธ์ (detection) — testing อยู่ใน QC
Q6: Flaky test เกิดจากอะไร แก้ยังไงA: จาก non-determinism เช่น sleep ตายตัว, shared state/ลำดับ, ข้อมูลไม่ reset, network/time จริง — แก้ให้ deterministic + isolate ข้อมูล แล้ว fix ทันทีโดยไม่ rerun หนี
Q7: Contract testing จับอะไรA: จับ breaking change ในสัญญา API ระหว่าง service ผู้ให้–ผู้ใช้ ก่อนไปพังจริงตอน deploy — ไม่ต้องพึ่ง E2E หนักๆ
