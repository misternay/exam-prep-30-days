11 · AI Fundamental: Coding Workflow

อ่าน ~35 นาที · อ้างอิงหลัก: Anthropic — Claude Code best practices; GitHub — spec-driven development; Google DORA 2024 report (AI adoption)

1. ต้องเข้าใจ

หลักคิดตั้งต้น

  • LLM ในงานเขียนโค้ด = “เพื่อนร่วมงานที่เร็วมาก แต่เพิ่งวันแรกในโปรเจกต์ทุกวัน” — รู้ภาษาและ pattern ทั่วไป แต่ไม่รู้ codebase, convention, ข้อตกลงของทีม → หน้าทีคุณคือให้ context และ verify
  • ความเสี่ยงหลักของ AI coding ตาม DORA: เพิ่ม throughput แต่ก็เพิ่ม instability ถ้าไม่มี test/review pipeline รองรับ — workflow ที่ดีจะไปด้วยกันกับ CI/CD คุณภาพสูง
  • กฎเหล็ก: “ยังไม่รัน = ยังไม่เสร็จ” — ผลลัพธ์ต้องผ่าน test/build จริง ไม่ใช่คำอธิบายว่าควรจะผ่าน

Loop การทำงานที่แนะนำ (จำแล้วใช้ตอบได้)

  1. Understand — ให้ agent สำรวจ/สรุปโค้ดที่เกี่ยวข้องก่อน (อ่านไฟล์จริง ไม่เดา); ถ้า task ใหญ่ ใช้ subagent สำรวจ
  2. Plan / Spec — เขียนแผนสั้นๆ หรือ spec: ต้องทำอะไร, ที่ไฟล์ไหน, acceptance criteria, test ที่จะเขียน — ให้คนอนุมัติแผนก่อนลงมือ (สำคัญสุดต่อคุณภาพ)
  3. Implement (small steps) — ทำทีละส่วนเล็กที่ review ได้; diff ใหญ่ = review แย่ = bug หลุด
  4. Verify — รัน test, build, lint, รันจริงดู behavior; ทดสอบ edge case ที่ AI มองข้าม (null, ขอบเขตตัวเลข, permission)
  5. Review — อ่าน diff ทุกบรรทัด เหมือน review คน — เพราะเราเป็นเจ้าของโค้ดที่ merge
  6. Commit — atomic commit + message อธิบาย; ผูกกับ issue/PR

Spec-driven development

  • เขียน spec/acceptance criteria ก่อนให้ AI ลงมือ — spec = สัญญาที่ใช้ตรวจได้ทั้ง “ก่อนสร้าง” และ “หลังสร้าง”
  • แยกงานใหญ่เป็น task ย่อยที่มีคำตอบชัด (ดีกว่า mega prompt ยาวๆ) — ให้ demo/test ได้ทีละส่วน
  • ใช้ rules file ของโปรเจกต์ (AGENTS.md / CLAUDE.md / .cursorrules) เก็บ: คำสั่ง build/test, สไตล์, convention ตั้งชื่อ, สิ่งที่ห้าม — ลดการอธิบายซ้ำทุก session

การจัดการ context ในการเขียนโค้ด

  • เปิดเฉพาะไฟล์ที่เกี่ยวข้อง; session สั้นต่อ 1 task (context ยาว = คุณภาพตก + เปลือง)
  • เมื่อ context เกือบเต็ม: สรุปงานค้างเป็น spec/handoff แล้วเริ่ม session ใหม่ (compaction); อย่าให้ agent ทำงานต่อด้วยความจำที่พร่ามัว
  • บอก constraints จริง: ภาษา/เวอร์ชัน, framework, ห้ามเพิ่ม dependency ใหม่, ต้องเข้ากับ style เดิม — AI ที่ไม่รู้ข้อจำกัดจะเลือกโซลูชันสวยแต่ใช้งานไม่ได้

Test กับ AI — TDD-enhanced

  • ให้เขียน test จาก spec ก่อน (หรือคนเขียน) → AI ทำโค้ดให้เขียว → refactor — เทสต์คือ safety net สำหรับ “โค้ดที่ AI ผลิตเร็วเกินจะเชื่อ”
  • เขียน regression test ทุกครั้งที่แก้ bug: ก่อนแก้สร้าง test ที่พัง (พิสูจน์ว่าเจอ bug จริง) → แก้ → test เขียว + suite เดิมไม่พัง
  • ระวัง AI “แก้ทดสอบให้ผ่าน” แทน “แก้โค้ดให้ถูก” — review test diff เข้มเท่า production code

ความเสี่ยงที่ต้องคุมใน workflow

  • Hallucinated API/package — ไลบรารีหรือฟังก์ชันที่ไม่มีจริง (หรือเป็นชื่อ package ปลอมใน registry = supply chain risk) → ตรวจกับเอกสารจริงก่อนใช้; pin version
  • Prompt injection ผ่านไฟล์/หน้าเว็บ — comment ในโค้ด, ไฟล์ใน repo, เนื้อหาเว็บที่ agent อ่าน อาจมีคำสั่งซ่อน → อย่าให้ agent มีสิทธิกว้างเกิน (least privilege), ตรวจ action อันตราย (ลบไฟล์, ส่งข้อมูลออก)
  • Secrets หลุดเข้า context — ไฟล์ .env / คีย์ที่อ่านเข้าไปอาจไปโผล่ใน log ที่อื่น; ใช้ secret manager + กันไฟล์ลับด้วย .gitignore/.claudeignore
  • Attribution & license — โค้ดจากโมเดลอาจคล้ายของมีลิขสิทธิ์ — นโยบายบริษัทเป็นตัวตัดสิน; commit message ควรบอกส่วนที่ AI ช่วย

วัดผลแบบมืออาชีพ

  • งานซ้ำ>1 ครั้ง → สร้าง eval: ชุดงานตัวอย่าง + เกณฑ์ผ่าน (test ผ่าน? diff ถูก pattern?) แล้ววัดก่อน/หลังเปลี่ยน prompt/skill
  • ติดตาม: cycle time, change failure rate ของงานที่ AI ช่วยเทียบกับงานปกติ (ไม่ใช่แค่ “รู้สึกเร็วขึ้น”)

2. ต้องจำ

  • Loop: Understand → Plan → Implement (small) → Verify → Review → Commit
  • “ยังไม่รัน = ยังไม่เสร็จ”
  • Spec/rules file ก่อนเริ่ม: AGENTS.md/CLAUDE.md เก็บคำสั่ง build/test + convention
  • TDD กับ AI: test ก่อน → เขียว → refactor; bug → regression test ก่อนแก้
  • Risk 3 ตัวท่อง: hallucinated API/package · prompt injection จาก content · secrets หลุดเข้า context
  • Diff เล็ก + review ทุกบรรทัด; AI ไม่ใช่ autopilot

3. กับดักข้อสอบ

  • “ให้ AI ทำ one-shot ทั้งฟีเจอร์” — คำตอบแย่; ที่ถูกคือ decompose + verify ทีละขั้น
  • “AI เขียนแล้ว build ผ่าน = เสร็จ” — ยังไม่เสร็จ; ต้อง test behavior + review
  • “ให้ AI แก้ test ให้ผ่าน” — สัญญาณอันตราย (แก้ที่ข้อสอบแทนแก้ที่โค้ด)
  • Prompt ยาวละเอียดไม่มีที่ติ = ดีเสมอ — ไม่จริง; ยาวเกิน context rot + ขัดกันเอง; ต้องมี spec/ตัวอย่างที่คม
  • AI ช่วยแล้วไม่ต้อง review — ผิด; คนที่ merge คือคนรับผิดชอบ

4. Self-check (ปิดหน้า ตอบก่อน)

Q1: เล่า agentic coding loop ที่ดีเป็นขั้นๆA: Understand (สำรวจโค้ดจริง) → Plan/spec + acceptance → Implement ทีละส่วนเล็ก → Verify (test/build/รันจริง) → Review diff ทุกบรรทัด → Commit atomic
Q2: ทำไม “ยังไม่รัน = ยังไม่เสร็จ”A: LLM อธิบายได้ดูถูกเสมอแม้โค้ดพัง — หลักฐานเดียวที่เชื่อได้คือ test/build/runtime จริงผ่าน; self-report ไม่ใช่หลักฐาน
Q3: Spec-driven development ช่วยอะไรA: เขียน spec + acceptance criteria ก่อนลงมือ → ใช้ตรวจทั้งก่อนและหลังสร้าง, ลดการตีความ, ทำให้ decompose งานได้ชัด และ AI ทำตามได้แม่นขึ้น
Q4: ยก 3 ความเสี่ยงหลักของ AI coding workflowA: (1) hallucinated API/package ปลอม (2) prompt injection จากไฟล์/เว็บที่ agent อ่าน (3) secrets/repo content หลุดเข้า context หรือ action เกินสิทธิ์
Q5: ถ้า context session ยาวมากจนเริ่มแย่ ควรทำอะไรA: สรุปงานค้าง/การตัดสินใจเป็น handoff หรือ spec แล้วเริ่ม session ใหม่ (compaction) — อย่าฝืนทำต่อด้วย context ที่เจือจาง
Q6: ทำไมต้องเขียน regression test ก่อนแก้ bug กับ AIA: พิสูจน์ว่า test จับ bug นั้นได้จริง (แดงก่อน) → แก้แล้วเขียว = ยืนยันว่าแก้ตรงจุด และกันกลับมาพังซ้ำ
Q7: “AI แก้ test ให้ผ่าน” ทำไมน่ากังวลA: เพราะมันรักษาความเขียวโดยลดความหมายของ test (ผ่อน assertion) แทนที่จะแก้โค้ดจริง — test diff ต้อง review เข้มเท่าโค้ด
ท่อง 3 อย่างวันนี้: loop 6 ขั้น · “ยังไม่รัน=ยังไม่เสร็จ” · risk 3 ตัว (hallucinated API / prompt injection / secrets)
