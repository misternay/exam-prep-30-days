07 · Version Control (Git)

อ่าน ~35 นาที · อ้างอิงหลัก: Pro Git book (git-scm.com/book) โดยเฉพาะบท 2–3, 7

1. ต้องเข้าใจ

โมเดลของ Git

  • Git เก็บ snapshot ของทั้งโปรเจกต์ ต่อ commit (ไม่ใช่ diff เป็นหน่วยหลัก) + ทุก commit อ้างถึง commit แม่ → เป็น DAG
  • มี 3 พื้นที่: Working Directory (ไฟล์ที่แก้) → Staging Area / Index (สิ่งที่เลือกจะ commit) → Repository (commits, HEAD ชี้อยู่)
  • HEAD = pointer ไปยัง commit/branch ปัจจุบัน; branch = pointer เบาๆ ที่ย้ายตาม commit ใหม่
  • Remote = repo อีกชุด (origin มักเป็นตัวกลาง); Git ทำงาน offline ได้เกือบทั้งหมดก่อน push

Workflow พื้นฐาน

git status            # ดูสถานะ 3 พื้นที่
git add <file>        # ย้ายเข้า staging (. เลือกทั้งหมด)
git commit -m "..."   # บันทึก snapshot (เฉพาะที่ stage)
git log --oneline --graph   # ดูประวัติ
git push / git pull   # sync กับ remote (pull = fetch + merge)

Branch & merge

  • git switch -c feature/x สร้าง+ย้าย branch; merge กลับเข้า main ได้จาก PR
  • Fast-forward merge — main ไม่มี commit ใหม่ → แค่เลื่อน pointer
  • Three-way merge — สองฝั่ง diverge → สร้าง merge commit (มี 2 parents); ถ้าชนบรรทัดเดียวกัน = conflict ต้องแก้มือ
  • Merge vs Rebase: merge เก็บประวัติจริง (มี merge commit) ปลอดภัยกับ shared branch; rebase เขียน commit ใหม่ให้เป็นเส้นตรง สวยกว่า แต่ ห้าม rebase commit ที่ push ไปแล้ว/คนอื่นดึงไปใช้ (history diverges)
  • Conflict แก้: เปิดไฟล์ → เลือก/รวมโค้ด → git add → git merge --continue (rebase ใช้ --continue เช่นกัน; --abort ถอยกลับ)
  • ใน rebase ความหมาย ours/theirs สลับกับที่คาด (ours = ฝั่งที่ rebase ไปวาง = upstream) — กับดักสนามจริง

ยกเลิก/กู้คืน — แยกให้ออก

คำสั่งทำอะไรใช้เมื่อ
git restore <file>คืน working tree ให้ตรง index (ใช้ --source=HEAD เพื่อคืนจาก commit)แก้เล่นแล้วไม่เอา
git restore --staged <file>เอาออกจาก staging (ไฟล์ไม่หาย)add ผิด
git commit --amendแก้ commit ล่าสุด (message/ไฟล์) — เขียน hash ใหม่ลืมไฟล์/พิมพ์ผิด (ยังไม่ push)
git reset --softย้าย branch pointer กลับ, เก็บ stagedรวม commit
git reset --mixed (default)ย้าย pointer + unstageแยก commit ใหม่
git reset --hardย้าย pointer + ทิ้ง staged/tracked changesระวัง! untracked ที่ขวางทางอาจถูกลบ
git revert <sha>สร้าง commit ใหม่ที่ “กลับด้าน” ของ commit นั้นundo บน shared branch (ปลอดภัย)
git stash / stash popพักงานที่แก้ไว้ชั่วคราวต้องสลับงานกลางคัน
git reflogประวัติการย้าย HEAD ทุกครั้งกู้ commit/branch ที่ reset หาย

คำสั่งประกอบอื่นๆ

  • git cherry-pick <sha> — ยก commit เดียวจากที่อื่นมาแปะบน branch ปัจจุบัน
  • git fetch vs git pull — fetch ดึงของใหม่มาไม่แตะ branch เรา; pull = fetch + merge (หรือ rebase ตาม config)
  • git tag v1.0.0 (annotated = -a) — tag release; git diff, git blame, git bisect (binary search หา commit ที่ทำพัง)
  • .gitignore — กันไฟล์ build/secret ไม่ให้เข้า repo; ไฟล์ที่เคย track ต้อง git rm --cached ก่อน
  • Detached HEAD — checkout ไปที่ commit ตรงๆ (ไม่ใช่ branch) → commit ใหม่จะลอย; แก้โดยสร้าง branch ณ จุดนั้นถ้าต้องการเก็บ

Branching strategy & team practice

  • Trunk-based — merge เข้า main บ่อยๆ (branch อายุสั้น) + feature flag → CI/CD ราบรื่น
  • GitFlow — มี develop/release/hotfix หลายสายสำหรับ release รอบยาว — หนัก ใช้เมื่อจำเป็นจริง
  • Pull Request flow: feature branch → PR (คำอธิบาย + linked issue) → review → CI เขียว → merge; ห้าม commit ตรงเข้า main ที่ protect ไว้
  • Commit hygiene: atomic (หนึ่งเรื่องต่อ commit), message บอก “ทำไม/ทำอะไร” (imperative เช่น “add rate limit to login”), อย่า commit ของครึ่งๆกลางๆ หรือ secret

2. ต้องจำ

  • 3 พื้นที่: working dir → staging → repo; HEAD/branch = pointer
  • reset vs revert: reset = เขียนประวัติทิ้ง/ย้าย pointer (local); revert = สร้าง commit กลับด้าน (shared ปลอดภัย)
  • ห้าม rebase ของที่ push แล้ว — กฎเหล็ก
  • pull = fetch + merge
  • กู้หาย: reflog
  • branch อายุสั้น + merge บ่อย = trunk-based CI/CD friendly

3. กับดักข้อสอบ

  • ถาม “undo commit ที่ push ไปแล้วบน main” → ตอบ revert ไม่ใช่ reset --hard
  • reset --hard ไม่ได้ “ผิดเสมอ” — ผิดเฉพาะบน shared/commit ที่ push (เขียนประวัติให้คนอื่นพัง)
  • merge ไม่ได้สร้าง commit เสมอไป (fast-forward) — ข้อสอบชอบถาม
  • “Git เก็บ diff ต่อ commit” — ไม่ตรงหลัก: เก็บ snapshot (บีบอัดเป็น delta ให้จัดเก็บเท่านั้น)
  • Conflict ไม่ใช่ error — เป็นสถานะปกติของ merge ที่ Git ให้คนตัดสิน

4. Self-check (ปิดหน้า ตอบก่อน)

Q1: อธิบาย 3 พื้นที่ของ GitA: Working directory (แก้ไฟล์อยู่), Staging/index (เลือกไว้จะ commit), Repository (commits + history) — git add ย้าย 1→2, git commit ย้าย 2→3
Q2: reset กับ revert ต่างกันเมื่อไรใช้อะไรA: reset ย้าย branch pointer/เขียนประวัติ — ใช้กับงาน local ที่ยังไม่แชร์; revert สร้าง commit ใหม่กลับด้านของ commit เป้าหมาย — ใช้กับ branch ที่ push/แชร์แล้ว
Q3: ทำไมห้าม rebase commit ที่ push แล้วA: rebase เขียน commit เป็นชุดใหม่ (hash เปลี่ยน) → สำเนาประวัติสองแบบชนกัน คนอื่นที่ดึงไปแล้วต้องแก้ chaos
Q4: กู้ commit ที่ reset --hard หายไป ยังไงA: git reflog ดูตำแหน่ง HEAD เก่า → checkout/branch/reset กลับที่ commit นั้น (ถ้า GC ยังไม่เก็บ)
Q5: Fast-forward merge คืออะไรA: merge ที่ branch ปลายทางไม่มี commit ใหม่ของตัวเอง — Git แค่เลื่อน pointer ไปข้างหน้า ไม่สร้าง merge commit
Q6: fetch ต่างจาก pullA: fetch ดึง refs/commits ใหม่มารอไว้ (ไม่แตะ working tree/current branch); pull = fetch แล้ว merge (หรือ rebase ตาม config) เข้า branch ปัจจุบัน
Q7: commit ที่ดีเป็นแบบไหน 3 ข้อA: atomic (เรื่องเดียว), message ชัดเข้าใจได้ (ทำอะไร/ทำไม), ไม่มี secret/ไฟล์ขยะ และ repo ยัง build/test ผ่าน ณ commit นั้น
ท่อง 3 อย่างวันนี้: ตาราง undo (restore/reset/revert/reflog) · กฎห้าม rebase ของที่ push แล้ว · pull = fetch + merge
