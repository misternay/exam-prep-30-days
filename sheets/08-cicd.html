เข้าใจต้องจำกับดักSelf-check

08 · CI/CD

อ่าน ~35 นาที · อ้างอิงหลัก: GitLab CI docs, GitHub Actions docs, Continuous Delivery (Humble & Farley), DORA metrics

1. ต้องเข้าใจ

CI (Continuous Integration)

  • แนวปฏิบัติ: merge โค้ดเข้า main บ่อยๆ (วันละหลายครั้ง) + ทุกครั้งที่ push/PR มี build + test อัตโนมัติ
  • เป้าหมาย: จับ integration bug ให้เร็วที่สุด ก่อนที่ branch จะ diverge ไกล — “merge hell” หายไป
  • ของคู่กัน: trunk-based development, PR เล็ก, test ที่เชื่อถือได้ (flaky น้อย)

CD — Delivery vs Deployment

  • Continuous Delivery — ทุก commit ที่ผ่าน pipeline “พร้อม deploy” ได้ตลอด; การขึ้น prod เป็นการตัดสินใจของคน (กดปุ่ม)
  • Continuous Deployment — ขึ้น prod อัตโนมัติทุก commit ที่ผ่าน gate โดยไม่มีคนกด
  • ข้อสอบชอบถามคู่ต่างนี้ตรงๆ — ท่องให้ได้ว่า Delivery = พร้อมเสมอ + คนกด, Deployment = อัตโนมัติถึง prod

Pipeline มาตรฐาน (เรียงตามลำดับ)

  1. Checkout (และ trigger: push / PR / tag / schedule)
  2. Install dependencies (pin version, cache ได้)
  3. Build / compile
  4. Unit test (เร็ว — รันก่อน)
  5. Static checks: lint, type check, SAST, secret scan, SCA (dependency CVE)
  6. Package → Artifact (jar/tarball/container image) → เก็บใน registry พร้อม version
  7. Deploy ไป environment: dev → staging/UAT → production
  8. หลัง deploy: smoke test / E2E / integration test
  9. Ops: migration, cache แจ้งเตือน, monitoring hook
  • Build once, deploy everywhere — artifact เดียวกันทุก env ต่างกันแค่ config/secrets (env vars) — อย่า build ใหม่ต่อ env
  • Quality gate — เงื่อนไขผ่าน เช่น tests ผ่านทั้งหมด, coverage ไม่ตกลง, ไม่มีช่องโหว่ระดับสูง; ไม่ผ่าน = หยุด (block merge)

Deployment strategies — ท่อง

กลยุทธ์วิธีจุดเด่น/ข้อเสีย
Recreateหยุดเก่า → เริ่มใหม่ง่ายสุด แต่ downtime
Rollingทยอยแทน instance ทีละชุดไม่ downtime แต่ช่วงเปลี่ยนผ่านมีสองเวอร์ชัน
Blue-Greenมีสอง environment สลับ trafficrollback เร็ว (สลับกลับ) แต่รันสองชุด = แพง/ต้อง DB compatible
Canaryส่ง traffic บาง % ไปเวอร์ชันใหม่ก่อนเสี่ยงต่ำ ค่อยขยาย; ต้องมี metric ตรวจ
Feature flagdeploy ได้แต่ปิดฟีเจอร์ด้วย flagแยก release ออกจาก deploy — เปิด/ปิดไม่ต้อง deploy
  • Rollback vs fix-forward — ระบบควร rollback ได้เร็ว (artifact เก่ายังอยู่), migration ต้องออกแบบ backward-compatible (expand → migrate → contract) ไม่เช่นนั้น rollback พัง

Pipeline as code & Infra

  • Pipeline เก็บเป็นไฟล์ใน repo: GitLab CI (.gitlab-ci.yml — stages: build, test, deploy + jobs/runners), GitHub Actions (.github/workflows/*.yml — on: push/PR + jobs/steps/runners)
  • Secrets ใน CI — เก็บใน CI secret store/Vault, inject ตอนรัน, ห้าม echo ใน log, mask ค่า
  • IaC — Terraform/CloudFormation: describe infrastructure เป็นโค้ด → review + version ได้, สร้าง env ซ้ำได้
  • Environments: dev (นักพัฒนาทำงาน) → staging/UAT (เหมือน prod, ให้ QA) → prod; promotion ด้วย artifact เดิม

DORA 4 metrics (วัดความเร็ว+คุณภาพ)

  • Deployment frequency — ออกบ่อยแค่ไหน · Lead time for changes — commit→prod ใช้เวลานานแค่ไหน
  • Change failure rate — deploy แล้วมีปัญหากี่ % · MTTR — กลับมาใช้ได้เร็วแค่ไหนเมื่อพัง
  • เร็ว 4 ตัวนี้ = ทีมระดับ elite (ตามงานวิจัย DORA)
  • อัปเดต: DORA ปี 2023 เปลี่ยนชื่อ MTTR → failed deployment recovery time; ปี 2024 เพิ่มตัวที่ 5 deployment rework rate — ข้อสอบส่วนใหญ่ยังใช้ “Four Keys” ชุดเดิม

2. ต้องจำ

  • CI = integrate+test อัตโนมัติทุก push; CD: Delivery = คนกด, Deployment = อัตโนมัติ
  • Pipeline stages เรียง: build → unit test → scan → package → deploy → smoke
  • Build once, deploy everywhere (artifact เดียว, ต่างที่ config)
  • Strategies 5 ตัว + ข้อดีเสียสั้นๆ
  • DORA 4: deploy frequency, lead time, change failure rate, MTTR (+ตัวที่ 5 rework rate เพิ่มปี 2024)
  • Rollback ผูกกับ backward-compatible migration

3. กับดักข้อสอบ

  • “Continuous Delivery เหมือน Continuous Deployment” — ต่างกันที่คนกดหรือไม่
  • “ต้อง build ใหม่สำหรับ prod เพื่อความมั่นใจ” — ผิด; ใช้ artifact เดิม (สิ่งที่ test คือสิ่งที่ deploy)
  • การ test เฉพาะบน staging ก่อน prod ไม่ใช่ข้อเสียของ CD — เป็นเรื่องปกติของ Delivery/Deployment ที่ดี
  • Feature flag ≠ branch ยาว — flag อยู่ในโค้ดที่ deploy แล้ว; branch ค้างนานคือศัตรูของ CI
  • Pipeline ที่ flaky (test เด้งมั่ว) ทำ team เสียศรัทธา — ต้อง fix ทันที ไม่ใช่ rerun จนผ่าน

4. Self-check (ปิดหน้า ตอบก่อน)

Q1: CI คืออะไรและทำไมต้อง merge บ่อยA: Continuous Integration = รวมโค้ดกับ main บ่อยๆ + build/test อัตโนมัติทุกครั้ง — ลด integration bug และ merge conflict ใหญ่
Q2: Continuous Delivery ต่างจาก Continuous DeploymentA: Delivery = ทุก commit ผ่าน pipeline พร้อมขึ้น prod เสมอ แต่คนตัดสินใจกด deploy; Deployment = ขึ้น prod อัตโนมัติทันทีที่ผ่าน gate
Q3: เล่า pipeline stages มาตรฐาน 6 ขั้นA: checkout → install/build → test (unit ก่อน) → static/security scan → package artifact → deploy env + smoke test (+promotion ต่อ env)
Q4: “Build once, deploy everywhere” ทำไมสำคัญA: สิ่งที่ test ผ่านคือ binary/image เดียวกับที่ขึ้น prod — ลดความเสี่ยง drift และประหยัดเวลา; env ต่างกันแค่ config/secrets
Q5: Canary กับ Blue-Green ต่างกันยังไงA: Blue-Green มีสอง environment เต็มสลับ traffic ทั้งหมด; Canary ปล่อย traffic ส่วนน้อยไปเวอร์ชันใหม่แล้วค่อยๆ เพิ่มตามผลตรวจ
Q6: ถ้า deploy มีปัญหากลาง prod ทางเลือกมีอะไรบ้างA: Rollback ไป artifact เก่า (ต้องเตรียมไว้ + migration backward-compatible) หรือ fix-forward ด้วย hotfix; เลือกตามความรุนแรงและสถานะข้อมูล
Q7: DORA 4 metrics มีอะไรบ้างA: Deployment frequency, Lead time for changes, Change failure rate, MTTR (Time to Restore Service) — ปัจจุบัน DORA เรียก “failed deployment recovery time” และเพิ่ม metric ที่ 5 (rework rate) ในปี 2024
