10 · Docker & Containerize

อ่าน ~35 นาที · อ้างอิงหลัก: Docker docs — Get started, Dockerfile best practices, 12-factor app

1. ต้องเข้าใจ

Container vs VM (คำถามเปิดคลาสสิก)

  • VM: มี kernel ของตัวเองในแต่ละเครื่อง → หนัก, บูตนาน, isolation แข็ง
  • Container: ใช้ kernel ร่วมของโฮสต์ — แค่ process ที่ถูกจำกัดด้วย namespaces (มองไม่เห็นกัน) + cgroups (จำกัด CPU/RAM) → เบา, เริ่มวินาที, portable
  • ประโยคทอง: “container ไม่ใช่ VM ขนาดเล็ก — มันคือ process ที่ถูกจองกรง”; จุดนี้ส่งผลกับ security (แชร์ kernel → escape ได้ถ้าช่องโหว่ kernel) และ persistence (container ตาย → ไฟล์หาย)

Image & Layer

  • Image = template อ่านอย่างเดียว สร้างจาก Dockerfile เป็นชั้นๆ (layers) — แต่ละคำสั่งสร้าง layer; image = ชั้นที่ซ้อนกัน
  • Container = image + writable layer บนสุด (ตอนรัน); ลบ container → ชั้นเขียนหาย
  • Layer caching: Docker cache layer ที่ “อินพุตเหมือนเดิม” — เรียงคำสั่งให้ ของที่เปลี่ยนบ่อยอยู่ท้าย (COPY package.json → install deps → แล้วค่อย COPY source) ไม่งั้น cache พังทุกครั้งที่แก้โค้ด
  • Tag: repo/name:tag — ใช้ version จริง (1.4.2) หรือ digest สำหรับ production; :latest ลอยได้ = ไม่ reproducible (กับดักข้อสอบ)
  • Registry: ที่เก็บ image (Docker Hub, GitLab Registry, ECR) — flow: build → tag → push → (เครื่องอื่น) pull → run

Dockerfile ที่ดี (ท่องหลัก)

# 1. multi-stage: stage build ใหญ่ → final เล็ก ไม่มี toolchain
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                # ใช้ lockfile = reproducible
COPY . .
RUN npm run build

FROM node:20-slim
WORKDIR /app
COPY --from=build /app/dist ./dist
USER node                 # ไม่รันเป็น root
EXPOSE 3000               # เอกสารประกอบ (ไม่ได้ publish จริง)
CMD ["node", "dist/server.js"]
  • Best practices: base image เล็ก/ официальный, pin version, multi-stage, ไม่มี secret ใน image (ใช้ env/secret mount), .dockerignore ตัด node_modules/.git ออกก่อน COPY, RUN รวมคำสั่งที่เกี่ยวกัน (ลด layer), HEALTHCHECK สำหรับ orchestrator
  • ENTRYPOINT vs CMD: ENTRYPOINT = คำสั่งหลักตายตัว; CMD = default ที่ถูก override ได้จาก command line; ถ้าใช้คู่กัน CMD = default args ของ ENTRYPOINT — ใช้ exec form ["exe","arg"] เสมอ (PID 1 รับ signal ถูก, ไม่มี shell zombie)

คำสั่งที่ต้องแม่น

docker build -t myapp:1.0 .          # build จาก Dockerfile ปัจจุบัน
docker run -d -p 8080:3000 --name web myapp:1.0
docker ps / docker ps -a             # container รันอยู่/ทั้งหมด
docker logs -f web                   # ดู log
docker exec -it web sh               # เข้าไปใน container ที่รันอยู่
docker stop web && docker rm web
docker images / docker rmi myapp:1.0
docker pull / docker push

จำแยก: run=สร้างจาก image, start/stop/rm=คุม container เดิม; exec=เข้าไปสั่งงานข้างใน

Data & Network

  • Stateless-first: container ควรไม่มี state ในตัว (12-factor) — state ไป DB/object storage/queue
  • ถ้าต้องเก็บไฟล์: Volume (Docker จัดการ, life-cycle แยกจาก container) vs Bind mount (ผูกโฟลเดอร์โฮสต์ — ใช้ตอน dev); ข้อมูลใน writable layer หายเมื่อ container ถูกลบ
  • Network: default bridge —ต้อง map port -p host:container; user-defined network — container เรียกกันด้วย “ชื่อ” ได้ (DNS ในตัว) เหมาะกับ multi-service
  • Docker Compose: นิยามหลาย service ใน docker-compose.yml (services, image/build, ports, volumes, environment, depends_on) → docker compose up -d — ใช้ dev/local stack

Orchestration (รู้ไว้ตอบต่อ)

  • Docker รัน container เดี่ยว; production หลายเครื่องใช้ orchestrator — Kubernetes: Pod (หน่วยเล็กสุด ห่อ 1+ container), Deployment (จัดการ replicas + rolling update), Service (stable DNS/load-balance), ConfigMap/Secret (config แยกจาก image)
  • แนวคิดที่ต้องพูดได้: desired state, self-healing (restart), scaling, rollout

2. ต้องจำ

  • Container = process + namespaces + cgroups แชร์ kernel; VM มี kernel เอง
  • Image = layers read-only; container = + writable layer (หายเมื่องานลบ)
  • Layer cache เรียง: ของเปลี่ยนน้อยบนสุด, เปลี่ยนบ่อยล่างสุด
  • คำสั่งชุด run/ps/logs/exec/stop/rm + แยก run vs start
  • ห้าม secret ใน image; ห้ามพึ่ง :latest ใน prod
  • Volume vs bind mount — persist data นอก container
  • ENTRYPOINT ตายตัว / CMD override ได้ / ใช้ exec form

3. กับดักข้อสอบ

  • “Container เก็บข้อมูลถาวรได้เอง” — ผิด; writable layer ตายกับ container → ใช้ volume
  • แก้ Dockerfile แล้ว build ใหม่ช้าเพราะ cache เสีย — ตรวจลำดับ COPY (ก็อป source ก่อน install = ตาย)
  • EXPOSE ไม่ได้เปิดพอร์ตจริง — เป็น metadata/เอกสาร; ที่เปิดจริงคือ -p (หรือ network ภายใน)
  • “Image กับ container อย่างเดียวกัน” — ผิดชัด; image = class, container = instance
  • Container ที่รันเป็น root ผิดหลัก least privilege — production ควร non-root USER
  • Compose ≠ orchestrator production (ไม่ self-heal/scale ข้ามเครื่อง) — อย่าตอบเกิน

4. Self-check (ปิดหน้า ตอบก่อน)

Q1: Container ต่างจาก VM อย่างไร (กลไก + ผลกระทบ)A: container แชร์ kernel โฮสต์ ใช้ namespaces/cgroups กัก process — เบา เร็ว; VM มี kernel ตัวเอง — แยกขาดกว่าแต่หนัก. ผลพวง: container isolation อ่อนกว่า + ข้อมูลใน container ไม่ถาวร
Q2: ทำไมต้อง multi-stage buildA: ให้ final image มีแค่ artifact + runtime ไม่พก toolchain/dependency ของขั้น build → image เล็กลง ปลอดภัยขึ้น
Q3: จัดลำดับ Dockerfile ยังไงให้ cache ทำงานA: เอาคำสั่งที่ input เปลี่ยนน้อยอยู่ก่อน (base, deps manifest) คำสั่งที่เปลี่ยนบ่อย (COPY source) ไว้ท้าย — แก้โค้ดแล้วไม่ต้อง install deps ใหม่
Q4: ข้อมูลใน container หายเมื่อไร จะเก็บยังไงA: หายเมื่อ container ถูกลบ (writable layer); เก็บด้วย volume หรือ bind mount (และหรือดัน state ไป DB/object storage)
Q5: ENTRYPOINT กับ CMD ต่างกันA: ENTRYPOINT คำสั่งหลักที่ตายตัวไม่ถูก override ง่าย; CMD ค่า default (คำสั่ง/args) ที่ผู้ใช้ override ได้ — ใช้คู่กัน = ENTRYPOINT + args default
Q6: ทำไม production ไม่ควรใช้ tag :latestA: ไม่ระบุเวอร์ชัน → pull ตอนไหนได้ของใหม่ไม่รู้ตัว, ไม่ reproducible, rollback ไม่ได้ — ใช้ version tag/digest
Q7: Pod/Deployment/Service ใน Kubernetes ต่างกันยังไงA: Pod = หน่วยรันเล็กสุด (1+ container); Deployment = คุมจำนวน replica + rolling update ของ Pod; Service = DNS/load-balancer หน้า Pod ให้ที่อยู่คงที่
