04 · AI Fundamental: Context Engineering

อ่าน ~35 นาที · อ้างอิงหลัก: Anthropic — Effective context engineering for AI agents; Prompt Engineering docs; Lost-in-the-Middle (Liu et al.)

1. ต้องเข้าใจ

Context Engineering คืออะไร

  • คือการออกแบบทุกอย่างที่อยู่ใน context window ณ จังหวะที่โมเดลถูกเรียก — system prompt, ประวัติ, เอกสารที่ retrieve, ผลลัพธ์ tools, ตัวอย่าง — ให้พอดีกับงาน
  • ยกระดับจาก “prompt engineering” (เขียนคำสั่งเก่ง) → “context engineering” (จัดระบบข้อมูลรอบการเรียกให้ถูกจังหวะ): prompt คือ subset ของ context
  • ใช้กับทั้งแชตบอตและ agent — agent ยิ่งต้องการเพราะวนหลายรอบแล้ว context โตขึ้นเรื่อยๆ

Context window = budget

  • ขนาด context window จำกัดเป็น token และทุกอย่างกินโควตานี้ร่วมกัน: system prompt + tools + history + retrieved docs + output
  • ใส่เยอะ ≠ ดีขึ้น: context rot — ข้อมูลเยอะเกินทำให้ความสำคัญเจือจาง, lost-in-the-middle — โมเดลจำต้น/ท้ายได้ดีกว่ากลาง
  • ผลลัพธ์: จัดลำดับความสำคัญ — ข้อมูลสำคัญสุดไว้ต้นและ/หรือท้าย, ตัด noise ออก, ให้ “น้อยแต่คม” ดีกว่า dump ยาว

องค์ประกอบของ context ที่ต้องรู้จัก

  • System prompt — persona, กติกา, convention, รูปแบบ output, ห้ามอะไร
  • Task prompt — สิ่งที่ต้องทำรอบนี้ ชัดและเจาะจง + มีเกณฑ์ความสำเร็จ
  • Few-shot examples — ตัวอย่าง input→output ที่ถูกต้อง แนะนำ 2–5 ตัว; ตัวอย่างดีกว่าคำอธิบาย
  • Retrieved context (RAG) — เอกสารที่ดึงมาใส่ให้โมเดลใช้ตอบ (ดูหัวข้อ RAG ด้านล่าง)
  • Tool results — ผลจาก API/ไฟล์/คำสั่ง ที่ป้อนกลับเข้า loop
  • Conversation history — โตขึ้นทุกเทิร์น ต้องบริหาร (ตัด/สรุป)
  • Output format — ระบุ schema/JSON ได้บ่อยเท่าที่จำเป็น; ลด ambiguity = ลด hallucination

Prompt patterns ที่ใช้จริง

  • Zero-shot / few-shot — ไม่มี/มีตัวอย่าง
  • Chain-of-Thought — ให้คิดทีละขั้น; แต่กับ reasoning model รุ่นใหม่ไม่ต้องบังคับ (มันคิดเอง) — เข้าใจแนวคิดไว้ตอบข้อสอบ
  • Role prompting — กำหนดบทบาท/ผู้ฟัง เพื่อคุมน้ำเสียงและระดับความลึก
  • Delimiters — ครอบข้อมูล untrusted ด้วย tag ชัด (เช่น <document>…</document>) กันชนกับคำสั่ง
  • Negative constraints ใช้น้อยๆ — บอก “ให้ทำอะไร” หลัก; ตัวอย่าง: “use markdown” ดีกว่า “don't use HTML”

RAG (Retrieval-Augmented Generation)

  • Pipeline: เอกสาร → chunk (ตัดเป็นก้อน มี overlap) → embed (เป็น vector) → เก็บใน vector DB → ตอนถาม: embed คำถาม → retrieve top-k ที่ใกล้สุด → (rerank) → ใส่เข้า context → generate คำตอบ
  • chunk size คือ trade-off: เล็ก = แม่นตำแหน่งแต่ขาดบริบท; ใหญ่ = มีบริบทแต่เสียงรบกวนเยอะ; overlap กันข้อมูลขาดรอยต่อ
  • Hybrid search = keyword (BM25) + semantic (vector) — มักครอบคลุมกว่ารอบเดียว แต่ไม่มีวิธีไหนชนะทุกกรณี ต้อง eval กับงานจริง; reranker ช่วยจัดอันดับให้แม่นขึ้น
  • วลีสำคัญสำหรับข้อสอบ: RAG = “ให้ ความรู้/ข้อมูล” ไม่ได้“เปลี่ยนพฤติกรรม” โมเดล

RAG vs Fine-tune vs Prompting vs Long-context

วิธีเหมาะกับจุดอ่อน
Prompting / few-shotงานทั่วไป กติกาเล็กน้อย — ลองก่อน เร็ว ถูกไม่เพิ่มความรู้ใหม่ จำกัดด้วย context
RAGความรู้สด/เฉพาะองค์กร/ต้องอ้างอิงได้คุณภาพขึ้นกับ retrieval; ต้องดูแล index
Fine-tuningพฤติกรรม/รูปแบบ/โทน/งานเฉพาะทางที่ต้องทำบ่อยๆแพง ต้องมีข้อมูลสะอาด อัปเดตช้า
Long contextงานก้อนใหญ่ครั้งคราว (ทั้ง repo, ทั้งเอกสาร)แพง/ช้า, คุณภาพกลางๆ ลด (rot/middle)

ลำดับตัดสินใจมาตรฐาน: ลอง prompt ก่อน → ไม่พอความรู้ = RAG → ยังไม่พอรูปแบบ/ฝังลึก = fine-tune

บริหาร context ในงานยาว

  • Compaction/Summarization — เมื่อ history ยาว สรุปให้สั้นลงแล้วลบของเก่า (agent ทำอัตโนมัติได้)
  • External memory — เขียนสิ่งที่ต้องจำลงไฟล์/DB แล้วอ่านคืนเมื่อต้องใช้ (เช่น notes.md, memory store) แทนการถือทั้งหมดใน context
  • Sub-agents / context isolation — แยกงานที่สำรวจเยอะให้ agent ลูก แล้วส่งกลับแค่ข้อสรุป (ประหยัด context แม่)
  • Tool-result hygiene — ตัด output เครื่องมือที่ยาวเกิน เช่น log หมื่นบรรทัด ให้เหลือหัว–ท้าย + สรุป
  • Truncation ที่ดี — ตัดกลางโค้งเดียว แต่รักษา: กติกา, งานปัจจุบัน, ความล้มเหลวล่าสุดที่ต้องรู้

2. ต้องจำ

  • นิยาม: Context engineering = จัดการ “ทุกอย่างที่อยู่ใน context window” ให้เหมาะกับงาน ไม่ใช่แค่ข้อความสั่ง
  • Lost-in-the-middle — ต้น/ท้ายเด่น กลางจาง → วางของสำคัญหัว–ท้าย
  • RAG pipeline 5 ขั้น: chunk → embed → store → retrieve → (rerank) → generate
  • RAG ให้ความรู้ / fine-tune ให้พฤติกรรม / prompting ลองก่อน
  • Compaction, memory แยก, sub-agent = 3 เทคนิคคุม context ยาว
  • Prompt injection จากเอกสารที่ retrieve ได้ = ความเสี่ยงประจำของ RAG (ข้อมูล untrusted ต้อง delim + ห้ามเชื่อคำสั่งในนั้น)

3. กับดักข้อสอบ

  • “RAG แก้ hallucination ได้ 100%” — ผิด; ช่วยGround แต่ไม่การันตี (retrieval พลาด/โมเดลยังแต่งได้)
  • “ใส่ context เยอะสุด = ดีสุด” — ผิด; มี cost, latency และ context rot
  • Few-shot ≠ fine-tune — ตัวอย่างใน prompt ไม่ได้เปลี่ยน weight โมเดล
  • “ให้โมเดลจำไว้ในความจำ”กับ “ใส่ใน context” — โมเดลไม่มี state ในตัวเองระหว่างเรียก; ความจำ = สิ่งที่ระบบเราใส่มาให้รอบใหม่
  • Chain-of-Thought บังคับกับ reasoning model เป็นข้อลวง — รุ่นใหม่คิดภายในอยู่แล้ว (ยังรู้ concept ว่าใช้เปิด reasoning งาน multi-step)

4. Self-check (ปิดหน้า ตอบก่อน)

Q1: Context engineering ต่างจาก prompt engineering ยังไงA: Prompt engineering ดูแค่ถ้อยคำคำสั่ง; context engineering ดูแลทุกอย่างที่ป้อนเข้าโมเดล (system, history, retrieved docs, tool output, ตัวอย่าง) ให้พอดี budget และจังหวะ
Q2: เล่า RAG pipeline เป็นขั้นๆA: chunk เอกสาร → embed เป็น vector → เก็บใน vector DB → ตอนถาม retrieve top-k → (rerank) → ใส่เป็น context → โมเดล generate จากข้อมูลนั้น (อ้างอิงได้)
Q3: เมื่อไรควร RAG เมื่อไรควร fine-tuneA: RAG เมื่อขาด “ความรู้” ใหม่/เฉพาะองค์กรหรือต้อง cite; fine-tune เมื่อต้องการ “พฤติกรรม/รูปแบบ” เฉพาะทางที่ prompting ล้วนทำไม่เสถียร
Q4: Lost-in-the-middle คืออะไร มีผลต่อการวาง context ยังไงA: โมเดลให้ความสำคัญกับ token ต้นและท้าย sequence ดีกว่าตรงกลาง → วางคำสั่ง/ข้อมูลสำคัญไว้ต้นหรือท้าย context
Q5: บอก 3 วิธีจัดการ context เมื่อบทสนทนายาวมากA: compaction/สรุปและตัดของเก่า; เขียนลง external memory (ไฟล์/DB) แล้ว retrieve คืน; แยกงานสำรวจให้ sub-agent แล้วรับเฉพาะบทสรุป
Q6: อะไรคือ context rot และทำไมเกี่ยวA: พอ context ยาวขึ้น คุณภาพการใช้ข้อมูลลดลง (ข้อมูลสำคัญเจือจาง) — เหตุผลว่าทำไมควรใส่ “น้อยแต่ตรง” และจัดลำดับ
Q7: Prompt injection จาก retrieved document กันยังไงA: ถือเอกสารเป็น untrusted — ครอบด้วย delimiter, ระบุห้ามทำตามคำสั่งในเอกสาร, แยก channel คำสั่งระบบกับข้อมูล, ตรวจสอบ action ก่อนรัน
